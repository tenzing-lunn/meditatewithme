01The product

What v1 actually is

A single page. You arrive, you see how many minutes until the next session and how many people are already waiting. At the top of the hour a candle lights, and a counter tells you how many people worldwide lit it with you. You set a timer between five minutes and an hour, choose the sounds you want underneath, and sit. A bell ends your session.

That is the entire product. It is also, stripped of its infrastructure, the entire idea — the client's spec spends twenty-three pages describing ways to deliver a feeling that this page delivers on its own.

Why this is the right v1 The thing being tested is not whether live video works. It is whether anyone shows up at 4am to sit with strangers. If they do, the live layer is worth building and there will be donations to fund it. If they don't, no amount of streaming infrastructure would have saved it.

03Architecture

Five decisions that make v2 cheap

"Right track to expand" is not a feeling, it's a set of specific seams. Each decision below is chosen so the live version slots in behind an interface that already exists, rather than forcing a rewrite.

1 · A session is a row type, not a feature

The client never asks "is this live?" It asks the session what to render. In v1 every session resolves to an ambient candle; in v2 some resolve to a stream. Same query, same component tree, one new branch in the player.

-- sessions rows are OVERRIDES, not the schedule itself
create table sessions (
  hour_start  timestamptz primary key,   -- always exactly on the hour, UTC
  kind        text not null default 'ambient'
              check (kind in ('ambient','live')),
  focus_slug  text not null default 'candle',
  stream_url  text,                        -- v2 only
  lighter_id  uuid references profiles(id) -- v2 only
);

2 · The schedule is computed, never stored

No cron job pre-creating 8,760 rows a year, no job queue, nothing to fall over at 3am. The current session is a pure function of the clock. A missing row is not an error — it's the ambient default, which is why the site can never be empty.

// the entire scheduler
export function currentHour(now = Date.now()) {
  const d = new Date(now);
  d.setUTCMinutes(0, 0, 0);
  return d;
}

// select * from sessions where hour_start = currentHour()
// no row  -> ambient candle. site is never empty.
// row     -> whatever it says. in v2, that's a live stream.
The seam This also settles the open question in the client's spec about time zones. One global session per hour, anchored to UTC, displayed in the viewer's local time. Everyone worldwide is in the same room. The alternative — top of the hour in each volunteer's local zone — means up to 24 parallel sessions and 24× the volunteers.

3 · Presence keyed by the hour

The participant count uses Supabase Realtime presence on a channel named after the current hour. The room rolls over by itself at the top of every hour with no cleanup code. In v2 the identical channel carries the live session's viewer count.

const room = supabase.channel(`session:${hourKey}`, {
  config: { presence: { key: anonId } }   // random per tab, not a user id
});
room.on('presence', { event: 'sync' }, () =>
  setCount(Object.keys(room.presenceState()).length)
);
room.subscribe(s => s === 'SUBSCRIBED' && room.track({}));

4 · Web Audio, not <audio> tags

Five loops mixing at independent volumes needs one AudioContext with a gain node per track. Audio elements drift out of sync and can't be ramped smoothly. Decode each buffer once, loop it natively, ramp the gain on change.

function track(ctx, buffer, master) {
  const src  = ctx.createBufferSource();
  const gain = ctx.createGain();
  src.buffer = buffer; src.loop = true; gain.gain.value = 0;
  src.connect(gain).connect(master);
  src.start();
  return v => gain.gain.linearRampToValueAtTime(v, ctx.currentTime + 0.15);
}

Two gotchas worth knowing now rather than in week two: an AudioContext cannot start without a user gesture, and iOS suspends it when the screen locks. Turn the first into the ritual — a single Begin tap that lights the candle and starts the audio. The constraint becomes the design.

5 · The timer reads the clock, it doesn't count

Browsers throttle setInterval to roughly once a minute in a background tab, and meditating with the tab hidden is the normal case. Store the target time and derive what's left; the countdown self-corrects after any sleep or tab switch.

const endsAt = Date.now() + minutes * 60_000;
const remaining = () => Math.max(0, endsAt - Date.now());

// schedule the bell on the AUDIO clock, not a JS timer,
// or it fires late in a backgrounded tab
bell.start(ctx.currentTime + remaining() / 1000);
04What it costs

Effectively nothing, and that's the point

The focus loops are short video files — a few megabytes, cached at the CDN edge, downloaded once per visitor. That is categorically different from streaming, where every viewer-minute is metered. Sound files behave the same way.

Supabase and Vercel free tiers cover the traffic a launching meditation site will see. Realistically the only recurring cost is the domain the client already owns.

Contrast with the original spec Live video at 25 average concurrent viewers, 24/7/365, runs roughly £10,000 a year in delivery alone — and scales upward with success, on a platform with no revenue. v1 removes that entire cost curve, plus the live-moderation and age-assurance obligations that come with broadcasting volunteers to an anonymous global audience.
05Build order

Three weeks, sequenced so it's safe to stop

Ordered by dependency, not by importance. The sequence matters: the product is complete and shippable after step 6, and everything after that is enhancement. If term work eats week three, you ship anyway.

Week 1 — the room

  1. 01Scaffold and deploy on day one4h Next.js App Router, Tailwind, Supabase project, Vercel, custom domain live with a holding page. Deploying first means never debugging deployment and features at once.
  2. 02Session engine3h currentHour(), override lookup, ambient fallback, next-session countdown. Pure functions, easy to unit test.
  3. 03The room itself8h Layout, candle loop, session clock in local time, the Begin gesture. This is the design work — spend the time here, it's the whole first impression.

Week 2 — the practice

  1. 04Timer and end bell5h Slider, wall-clock countdown, bell scheduled on the audio clock. Decide what happens when a timer ends inside a running session — fade, or stay.
  2. 05Sound mixer7h Web Audio graph, 5 tracks, per-track and master volume, preferences to localStorage. Blocked on the client sourcing licensed audio — chase this now.
  3. 06Live participant count3h Realtime presence, hour-keyed channel, plus a toggle to hide the number for anyone who finds it distracting.
The cut line. Everything above is a complete product for guests. Preferences live in localStorage, so the account layer below is purely a sync mechanism — bolt-on, not load-bearing.

Week 3 — the wrapper

  1. 07Accounts and synced preferences6h Supabase magic-link auth — no passwords means no reset flow. One preferences table, one RLS policy. On first login, push whatever's in localStorage up. This is the step most likely to overrun; it's last for that reason.
  2. 08Legal, polish, launch5h Privacy notice, terms, age gate, favicon and Open Graph, mobile QA on a real phone, keyboard navigation, prefers-reduced-motion.

Total41 hours

One RLS policy, and why it matters create policy "own prefs" on preferences for all using (auth.uid() = user_id) with check (auth.uid() = user_id); — the using clause governs what rows a user can read and delete; the with check clause governs what they're allowed to write. Omit the second and a user can update someone else's row by changing the id. Both, always.
06Risks

Where this actually goes wrong

  • Audio assets never arrive. The single hardest external dependency. Good singing bowl and Tibetan bell recordings that hold up on decent headphones cost money and someone has to buy them. Without them step 5 stalls. Chase it in week one, not week two.
  • Auth overruns. RLS is new to you and the first policy you write will be wrong in an interesting way. It's scheduled last and marked cuttable precisely so this can't sink the launch.
  • Scope creep from the original spec. The 23-page document will keep exerting pull. The §02 table is the defence — agree it in writing before starting and treat additions as separately quoted work.
  • The client hears "no live video" as "no product". Frame it as sequencing funded by evidence, not as a cut. Live becomes v2, paid for by donations v1 proves exist.
  • Nobody shows up. The real risk, and the one worth running. Better discovered in three weeks for almost nothing than after a year of building the full platform.
07Blocked on

Needed from the client before step 1

  • Registrar access to the domain confirmed, auto-renew and transfer lock on A 20-year-old domain lapsing mid-project is unrecoverable. Verify he is the registrant, not an agency from 2006.
  • Budget and sourcing for licensed audio Five ambient loops and three bells. Blocks step 5.
  • Three focus-point visuals, licensed Candle plus two. Seamless loops, sourced or commissioned.
  • The legal entity behind the site, and who is named as data controller Cannot write the privacy notice without it. Also gates donations.
  • Minimum age decided — 18+ recommended Reversible later. A safeguarding incident is not.
  • Written agreement on the §02 scope table Before any code. This is the only real protection against the other twenty pages.
